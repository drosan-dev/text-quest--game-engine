# Post-MVP Roadmap

Связанные документы:

- `docs/README.md` - карта документации.
- `docs/current-state.md` - что реально реализовано в репозитории сейчас.
- `docs/technical-vision.md` - архитектурные границы и точки расширения.
- `docs/authoring-quest-format.md` - текущий authoring-слой, который должен дальше развиваться без слома runtime-контракта.
- `docs/json-quest-format.md` - фактический контракт JSON-квеста, который будет расширяться по мере поставки этапов.

Этот документ описывает ближайшее развитие движка после завершения MVP. Он не фиксирует фактически реализованное поведение и не должен использоваться как источник истины для текущего runtime.

## 1. Фокус Следующего Этапа

Следующий этап должен оставаться в рамках универсального движка текстовых квестов и не вводить пока что специализированные мета-механики вроде повторяющихся забегов, выбора персонажа или глобальной симуляции мира между прохождениями.

Приоритет на этом этапе:

- сохранить платформенно-нейтральную архитектуру
- расширять декларативность формата квеста, а не вшивать новую логику в UI
- добавлять функции, полезные для широкого класса текстовых квестов, а не только для одного конкретного сеттинга
- усиливать выразительность контента без разрастания дублирующихся узлов и текста

## 2. Целевые Возможности

Ближайший post-MVP этап должен добавить три большие возможности:

- authoring-слой поверх runtime JSON, снижающий объем ручной служебной разметки для сценариста
- систему фактов или ачивок, интегрированную в runtime и JSON-контракт квеста
- условный шаблонизатор текста, позволяющий менять отдельные фрагменты строки и блока по фактам
- рандомизируемые текстовые пулы для вариативного текста и контентных вставок

Эти возможности должны проектироваться как базовые движковые примитивы, которые затем можно будет использовать и в простом линейном квесте, и в более сложных нарративных структурах.

## 3. Этап 0 [ ]. Авторский Слой Контента

### Цель

Упростить сценаристу написание квеста, оставив текущий runtime JSON стабильным внутренним контрактом движка и добавив поверх него более короткий authoring-формат.

### Зачем Это Нужно

- убрать из авторской работы большую часть технического шума вроде многословных `conditions` и `effects`, оставив только те явные `choice.id`, которые нужны для стабильности save/load и decision history
- сохранить строгую валидацию и предсказуемый runtime-контракт для движка и адаптеров
- дать возможность постепенно развивать authoring DX без переписывания runtime и save/load flow
- поддержать параллельную работу двух режимов: прямой runtime JSON и authoring-слой с компиляцией

### Минимальный Объем

Нужно поддержать:

- отдельный authoring-формат, компилируемый в текущую доменную модель
- сокращенные формы для переходов, условий и эффектов
- явные стабильные `choice.id` в authoring-контенте, чтобы не ломать save/load и decision history при правках текста
- явный выбор между runtime JSON и authoring-слоем при запуске CLI или другого адаптера
- единый runtime-валидатор после компиляции authoring-квеста

### Требования К Интеграции В Контент

Authoring-слой должен позволять автору:

- описывать сцены объектом `sceneId -> scene`, а не массивом полных runtime-узлов
- писать `goto` вместо `nextNodeId`
- писать `when` и `do` в краткой форме, например `hasKey`, `'!hasKey'`, `resolve >= 1`, `resolve += 1`
- оставаться в пределах декларативного контента, не переходя к scripting-языку общего назначения

Важно, чтобы authoring-слой был компиляционной прослойкой, а не альтернативным runtime. Источником истины для исполнения должен оставаться единый доменный контракт после компиляции.

### Ожидаемые Пользовательские Сценарии

- сценарист пишет короткий authoring YAML без ручного дублирования runtime-полей
- разработчик запускает тот же квест либо как уже собранный runtime JSON, либо как authoring-исходник через флаг
- редактор или tooling в будущем работают с authoring-слоем, не ломая стабильный runtime-контракт

### Технические Подзадачи

1. Зафиксировать минимальный authoring-контракт и документировать его отдельно от runtime JSON.
2. Добавить loader/compiler из authoring YAML в `QuestDefinition`.
3. Подключить повторное использование существующего runtime-валидатора после компиляции.
4. Добавить переключение формата входного квеста через флаг запуска CLI.
5. Добавить примеры контента и tests для двух режимов загрузки.

### Порядок Реализации

1. Сначала описать authoring-контракт и его границы.
2. Затем реализовать компиляцию в доменную модель.
3. После этого подключить выбор формата в CLI.
4. Затем обновить демо-контент и документацию.

## 4. Этап 1 [ ]. Система Фактов И Ачивок

### Цель

Добавить в движок новый слой состояния, который хранит значимые события и достижения прохождения в виде именованных фактов.

На этом этапе факты не должны иметь TTL, времени жизни по дням или механики истечения. Нужна только устойчивая, понятная и расширяемая модель постоянных фактов.

### Зачем Это Нужно

- открывать или блокировать ветки квеста на основе значимых событий
- отделить "сюжетно значимый факт" от обычных технических флагов и числовых переменных
- сделать условия в контенте понятнее для автора квеста
- дать автору способ шаблонизировать текст сцены без копирования почти одинаковых узлов
- подготовить основу для более богатой реактивности текста и выбора в будущих этапах

### Минимальный Объем

Нужно поддержать:

- хранение набора фактов в игровом состоянии
- эффекты, которые устанавливают факт
- опционально эффекты, которые снимают факт, если это не противоречит простоте модели
- условия, проверяющие наличие или отсутствие факта
- использование фактов при вычислении доступности выборов
- использование фактов в автоматических `branch`-узлах
- использование фактов при формировании текста события
- шаблонизацию отдельных строк, абзацев или вставок внутри одного узла по фактам

### Требования К Интеграции В Контент

Формат JSON-квеста должен позволять автору:

- добавить эффект наподобие `unlock_fact` или `set_fact`
- проверять факт в `conditions`
- использовать один и тот же узел, но показывать разные текстовые фрагменты в зависимости от факта
- описывать условные текстовые вставки декларативно, без дублирования почти всего текста узла

Важно сохранить совместимость концепции с текущей моделью `conditions` и `effects`, а не вводить отдельную, несвязанную mini-language систему.

Приоритет здесь именно на легком встроенном шаблонизаторе текста, а не на сложном scripting-языке. Автор должен уметь сказать: если факт есть, покажи этот фрагмент, иначе другой, не создавая новый узел только ради одной изменившейся строки.

### Ожидаемые Пользовательские Сценарии

- вариант выбора доступен только если у игрока есть определенная ачивка
- альтернативная концовка открывается только после получения факта в более ранней ветке
- один и тот же узел показывает другой текст, если ранее было совершено значимое действие
- один и тот же абзац или реплика содержат разные вставки в зависимости от полученных ачивок
- автор квеста может описывать важные сюжетные состояния более явно, чем через произвольные флаги

### Технические Подзадачи

1. Расширить `GameState` набором фактов.
2. Добавить доменную модель для эффекта установки факта.
3. Добавить поддержку проверки факта в condition evaluator.
4. Расширить JSON-десериализацию и валидацию под новые типы условий и эффектов.
5. Спроектировать минимальный условный шаблонизатор текста для узлов и текстовых блоков.
6. Расширить presentation/runtime flow так, чтобы текст узла мог зависеть от фактов без дублирования всего узла.
7. Добавить unit и integration tests на gating выборов, ветвлений и текста по фактам.
8. Обновить `docs/json-quest-format.md`, `docs/technical-vision.md` и `docs/current-state.md` после реализации.

### Порядок Реализации

1. Сначала добавить факты как часть доменного состояния и runtime.
2. Затем подключить их к условиям и эффектам.
3. Затем расширить текстовую модель узла для условных текстовых вариаций.
4. После этого зафиксировать минимальный синтаксис шаблонизации в JSON-контракте.
5. Затем покрыть сценарии тестами.

## 5. Этап 2 [ ]. Рандомизируемые Текстовые Пулы

### Цель

Добавить декларативный механизм случайного выбора текстовых фрагментов из заранее заданного пула, чтобы контент оставался вариативным без размножения почти одинаковых узлов.

### Зачем Это Нужно

- уменьшить копипасту в контенте
- сделать повторные прохождения менее однообразными
- поддержать газеты, фоновые сообщения, вариации реплик и flavor-text
- сохранить при этом детерминированность и тестируемость runtime

### Минимальный Объем

Нужно поддержать:

- объявление текстового пула в контенте квеста
- выбор одного случайного варианта из пула
- опционально выбор нескольких неповторяющихся вариантов, если это не усложнит контракт непропорционально
- встраивание результата в текст узла или отдельный блок отображения
- воспроизводимость при одинаковом seed, если в движке уже появится или будет добавлен управляемый источник случайности

### Важные Ограничения

- рандом не должен быть зашит в CLI или другой frontend
- API случайности должен быть инкапсулирован в runtime, чтобы его можно было стабильно тестировать
- формат контента должен оставаться читаемым для автора квеста
- если рандом влияет на прохождение, его влияние должно корректно сохраняться в `GameState`, чтобы загрузка не меняла уже показанный результат

### Ожидаемые Пользовательские Сценарии

- в сцене случайно выбирается одна из нескольких реплик
- в газете или сводке выводится случайный заголовок из пула
- при повторном посещении похожих сцен игрок видит разные flavor-вставки
- автор может использовать вариативность текста без создания отдельных дублирующих узлов

### Технические Подзадачи

1. Определить модель хранения текстовых пулов в JSON-контенте.
2. Ввести runtime-абстракцию для источника случайности.
3. Определить, когда именно производится выбор случайного текста: при входе в узел, при построении представления или при применении специального эффекта.
4. Зафиксировать правило сохранения результата, если он должен быть стабилен после save/load.
5. Добавить валидатор пулов и ссылок на них.
6. Добавить tests на детерминированность, корректность диапазона выбора и поведение после загрузки сохранения.
7. Обновить factual-документацию после поставки.

### Порядок Реализации

1. Сначала ввести абстракцию случайности и покрыть ее тестами.
2. Затем описать минимальный JSON-контракт для пулов.
3. Затем встроить использование пулов в presentation layer узла.
4. После этого решить, нужен ли выбор нескольких элементов или достаточно одного варианта в первой итерации.

## 6. Рекомендуемый Порядок Поставки

Ближайшая последовательность должна быть такой:

1. Authoring-слой поверх runtime JSON и переключение между режимами загрузки.
2. Система фактов как новое доменное состояние и новый тип условий и эффектов.
3. Условный шаблонизатор строк и текстовых блоков внутри существующей модели узлов.
4. Абстракция случайности в runtime.
5. Текстовые пулы и их использование в отображаемом тексте.
6. Обновление документации и примеров контента.

Такой порядок полезен потому, что сначала снижается стоимость написания контента и фиксируется authoring-слой, затем усиливается управляемая реактивность через факты и шаблонизацию, а потом поверх нее добавляется вариативность текста.

## 7. Что Пока Не Входит В Этот Этап

Сознательно не включать в ближайший план:

- TTL для фактов и временные эффекты
- выбор персонажа между прохождениями
- общий мировой state между несколькими разными сессиями персонажей
- day loop и мета-прогрессию между забегами
- процедурную генерацию сюжета
- адаптер-специфичную логику для Telegram, desktop или mobile

Эти направления можно будет планировать отдельно, когда базовые примитивы фактов и вариативного текста будут стабилизированы в универсальном движке.

## 8. Критерий Завершения Этапа

Этап можно считать завершенным, когда движок позволяет автору квеста:

- писать квест в коротком authoring-формате и при необходимости переключаться на прямой runtime JSON
- задавать значимые постоянные факты прямо в JSON-контенте
- открывать и закрывать выборы и ветки по фактам
- менять текст сцены, отдельных строк и вставок по фактам без дублирования всей сцены
- использовать случайные текстовые пулы для вариативных фрагментов
- сохранять и загружать игру без потери уже вычисленных последствий и уже показанных текстовых результатов там, где нужна стабильность
