# Готовые промпты

Шаблоны для генерации и уточнения проектной документации. Используются как вспомогательный материал и не заменяют документы-источники истины из `docs/README.md`.

## 1. Prompt For GDD Expansion

```text
Сформируй расширенный game design document для универсального движка текстовых квестов на .NET.

Контекст:
- движок не привязан к конкретному сюжету
- один и тот же квест должен запускаться через CLI, desktop UI, mobile app и Telegram bot
- квесты описываются декларативно, предпочтительно через JSON
- движок должен поддерживать ветвящиеся диалоги, последствия выборов, переменные состояния, условия доступности выборов и несколько финалов
- игра должна поддерживать сохранение и загрузку прогресса с полным восстановлением текущего места и всех значимых выборов

Что нужно на выходе:
1. Product vision
2. Goals and non-goals
3. Player-facing capabilities
4. Author-facing capabilities
5. Narrative model
6. State and consequence model
7. Save/load expectations
8. Portability requirements
9. Functional requirements
10. Success criteria

Требования к ответу:
- язык: русский
- без привязки к конкретному сюжету
- без воды, с инженерной точностью
- оформить как документ, который можно передать техкоманде и геймдизайнеру
```

## 2. Prompt For Technical Vision

```text
Сформируй техническое видение универсального движка текстовых квестов на .NET.

Контекст:
- движок должен быть ядром для нескольких интерфейсов: CLI, desktop UI, mobile app, Telegram bot
- игровая логика должна жить в независимом core-слое
- квесты описываются внешними JSON-файлами
- должны поддерживаться сцены, диалоги, выборы, условия, эффекты, ветвления, сохранения и загрузка
- важна переиспользуемость, тестируемость и минимальная связность между core и UI

Что нужно на выходе:
1. Архитектурный стиль и границы слоев
2. Список рекомендуемых проектов внутри solution
3. Основные доменные сущности
4. Runtime flow новой игры, хода игрока и загрузки сохранения
5. Подход к save/load
6. Точки расширения
7. Предлагаемый JSON-формат квеста
8. Пример JSON-файла
9. Правила валидации контента
10. Технические риски и меры снижения

Требования к ответу:
- язык: русский
- ориентир на .NET 10
- решение должно быть минимальным, но масштабируемым
- не предлагать лишнюю сложность для MVP
```

## 3. Prompt For MVP Plan

```text
Сформируй реалистичный план реализации MVP универсального движка текстовых квестов на .NET.

Контекст:
- сначала делаем движок, а не конкретный квест
- первый адаптер: CLI
- затем архитектура должна позволять без переписывания ядра добавить Telegram bot, desktop UI и mobile app
- квесты загружаются из JSON
- должны поддерживаться выборы, ветвления, состояние, последствия, сохранение и загрузка

Что нужно на выходе:
1. Цель MVP
2. Что входит в MVP и что не входит
3. Milestones с правильным порядком поставки
4. Acceptance criteria для каждого milestone
5. Стратегия тестирования
6. Рекомендованный первый end-to-end slice
7. Roadmap после MVP

Требования к ответу:
- язык: русский
- без абстрактных советов
- с приоритетом на маленькие корректные шаги
- с акцентом на переиспользуемую архитектуру
```

## 4. Prompt For JSON Schema Iteration

```text
Спроектируй минимальный, но расширяемый JSON-формат для движка текстовых квестов.

Контекст:
- формат должен описывать квест без привязки к UI
- нужны: quest metadata, start node, nodes, text blocks, choices, conditions, effects, branch nodes, end nodes, initial variables
- сохранение состояния хранится отдельно, но формат квеста должен быть совместим с этим подходом
- целевая реализация: .NET 10

Что нужно на выходе:
1. Структура файла верхнего уровня
2. Минимальный набор типов узлов
3. Формат conditions
4. Формат effects
5. Пример полного JSON
6. Какие поля обязательные, какие опциональные
7. Какие правила валидации нужны для надежного runtime

Требования к ответу:
- язык: русский
- ориентир на MVP, без тяжелого DSL
- схема должна быть удобной для машинной валидации и ручного редактирования
```

## 5. Prompt For Adapter Strategy

```text
Опиши стратегию адаптации универсального движка текстовых квестов под разные интерфейсы: CLI, desktop UI, mobile app и Telegram bot.

Контекст:
- есть единое .NET-ядро движка
- UI не должен содержать игровую логику
- каждый адаптер должен использовать общий application API
- игра должна поддерживать одинаковую бизнес-логику и одинаковые сохранения на всех платформах

Что нужно на выходе:
1. Общий контракт между движком и UI
2. Что должен делать frontend, а что должен делать core
3. Особенности каждого адаптера
4. Порядок реализации адаптеров
5. Риски по каждому адаптеру
6. Какие компромиссы допустимы в MVP

Требования к ответу:
- язык: русский
- прагматичный подход
- без UI-специфичных деталей, которые ломают переносимость
```

## 6. Prompt For Post-MVP Stage 2 (Random Text Pools)

```text
Нужно реализовать этап 2 из `docs/post-mvp-roadmap.md`: «Рандомизируемые текстовые пулы» в универсальном движке текстовых квестов на .NET.

Контекст:
- проект уже поддерживает загрузку квеста из JSON, runtime, presentation слой и save/load
- рандом не должен быть зашит в CLI/UI; источник случайности должен жить в runtime и быть тестируемым
- если рандом влияет на показываемый текст, результат должен сохраняться в `GameState`, чтобы после save/load он не менялся
- формат контента должен оставаться читаемым и валидируемым

Что нужно спроектировать и реализовать:
1) Минимальный JSON-контракт для текстовых пулов (где объявляются пулы, как на них ссылаться из текста/блоков).
2) Runtime-абстракцию источника случайности (seed/детерминированность).
3) Правило момента выбора (когда происходит выбор) и правило стабилизации результата в `GameState`.
4) Валидацию пулов и ссылок на них (ошибки формата, отсутствующие ключи, пустые/некорректные пулы).
5) Интеграцию в presentation/runtime flow: чтобы узел/блок мог использовать пул без дублирования узлов.
6) Tests: детерминированность при фиксированном seed, корректные границы выбора, поведение после save/load.
7) Обновление factual-документации: `docs/json-quest-format.md` и `docs/current-state.md` (и при необходимости `docs/technical-vision.md`).

Ограничения и решения по умолчанию:
- первая итерация: выбор ровно одного варианта из пула (без выбора нескольких неповторяющихся элементов), если иное не требуется текущей архитектурой
- запрещено добавлять UI-специфичную логику в core
- решение должно быть минимальным, но расширяемым (чтобы позже можно было добавить выбор нескольких элементов)

Критерии приемки:
- контент может объявлять пул и ссылаться на него в тексте узла/блока
- при одинаковом seed и одинаковом ходе игры выбор повторяемый
- после сохранения и загрузки уже выбранные варианты не меняются
- некорректный JSON контент получает понятную ошибку валидации
- покрыто тестами ключевое поведение (включая save/load)

Формат ответа/результата:
- короткий дизайн-док (пункты: JSON-контракт, state, момент выбора, сохранение, тестирование)
- затем patch: изменения кода + тесты + обновленные документы
```
