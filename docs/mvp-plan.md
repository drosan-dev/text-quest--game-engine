# План MVP

## 1. Цель MVP

Поставить переиспользуемый .NET-движок текстовых квестов, который умеет:

- загружать квест из JSON
- запускать ветвящийся квест
- отслеживать состояние и последствия выборов
- сохранять и восстанавливать прогресс
- работать через CLI-фронтенд без встраивания UI-логики в ядро

Общее уточнение по проекту:

- целевая платформа MVP и дальнейших этапов: `.NET 10`

## 2. Объем MVP

Входит:

- ядро движка
- JSON-формат квеста
- валидация квеста
- переменные и флаги состояния
- ветвящиеся выборы
- узлы ветвления
- сохранение и загрузка
- CLI-адаптер
- автотесты

Не входит:

- редактор квестов
- боевая система
- scripting-язык
- локализация
- облачные сохранения
- богатый desktop/mobile UI в первой поставке

### Этап 2 [x]. Загрузка И Валидация Контента

- реализовать JSON-loader
- реализовать структурную валидацию
- возвращать понятные ошибки валидации

Критерии приемки:

- невалидные файлы квестов отбрасываются до runtime
- валидный пример квеста успешно загружается

Рабочий промт на выполнение этапа:

```text
Реализуй Этап 2 MVP для универсального движка текстовых квестов на .NET 10: загрузку JSON-квеста и структурную валидацию контента.

Контекст проекта:
- архитектура: компактный Ports and Adapters
- каркас solution и базовые доменные модели уже созданы на Этапе 1
- поддерживаемые типы узлов для MVP: text, decision, branch, end
- демонстрационный квест уже лежит в репозитории и должен стать главным happy-path fixture
- runtime на этом этапе еще не реализуется, поэтому все ошибки контента должны выявляться до запуска игры

Что нужно сделать:
1. Реализовать JSON-loader в `TextQuest.Content.Json`, который читает файл квеста и преобразует его в доменные модели.
2. Реализовать структурную валидацию квеста: обязательные поля, корректные типы узлов, наличие стартового узла, существование целевых переходов, корректную форму choices/branches/end-result.
3. Возвращать понятные ошибки валидации с кодом, сообщением и путем к проблемному месту.
4. Обеспечить поведение, при котором невалидный квест не доходит до runtime.
5. Добавить автотесты на успешную загрузку демонстрационного квеста и на отклонение невалидного JSON/квеста.

Ограничения:
- не реализовывать игровой runtime, применение эффектов и вычисление условий
- не добавлять избыточную схему, генераторы или внешний DSL
- держать загрузчик и валидатор изолированными от CLI
- изменения должны оставаться минимальными и поддерживать последующий Этап 3

Критерии приемки:
- валидный демонстрационный JSON успешно загружается в доменные модели
- невалидные квесты отклоняются до runtime
- ошибки валидации читаемы и содержат контекст
- тесты покрывают happy path и хотя бы несколько failure-path сценариев

В ответе после выполнения:
- перечисли, какие классы/контракты были реализованы или добавлены
- кратко опиши, какие правила валидации покрыты
- укажи, какие сценарии проверяются тестами
- отдельно отметь, что runtime по-прежнему не реализован
```

### Этап 3 [x]. Core Runtime

- запуск новой игры
- получение текущего представления состояния
- применение выбора
- обработка следующего узла
- поддержка конечных узлов

Критерии приемки:

- демонстрационный квест проходится end-to-end без save/load

Рабочий промт на выполнение этапа:

```text
Реализуй Этап 3 MVP для универсального движка текстовых квестов на .NET 10: core runtime для запуска новой игры, показа текущего состояния и применения выборов.

Контекст проекта:
- архитектура: компактный Ports and Adapters
- каркас solution, доменные модели и JSON-loader с валидацией уже реализованы на предыдущих этапах
- runtime должен оставаться независимым от CLI и любых UI-деталей
- целевой runtime API должен возвращать не только представление для фронтенда, но и актуальный `GameState`, чтобы подготовить основу для последующего save/load
- поддерживаемые типы узлов для текущего этапа: `text`, `decision`, `branch`, `end`
- существующий демонстрационный квест должен проходиться end-to-end уже на этом этапе
- в текущем demo quest уже используются простые conditions/effects, поэтому допустимо реализовать минимальный runtime-support только в объеме, необходимом для прохождения существующего fixture, не превращая это в полноценный этап 4

Что нужно сделать:
1. Реализовать core runtime в application-слое с запуском новой игры от `startNodeId`.
2. Возвращать текущее состояние в двух формах: машинное (`GameState`) и представление для фронтенда (`PresentableState`).
3. Реализовать применение выбора, переход к следующему узлу, накопление истории решений и visited nodes.
4. Поддержать автоматическую обработку branch-узлов до ближайшего интерактивного или конечного узла.
5. Поддержать конечные узлы с корректным признаком завершения и result.
6. Добавить минимальную обработку conditions/effects только в объеме, который уже требуется демонстрационному квесту.
7. Добавить автотесты на старт игры, применение корректного и некорректного выбора, восстановление представления из `GameState` и end-to-end прохождение demo quest.

Ограничения:
- не реализовывать файловое save/load-хранилище на этом этапе
- не переносить runtime-логику в CLI, JSON-loader или infrastructure
- не добавлять тяжелый scripting/DSL для условий и эффектов
- держать публичный API минимальным, но пригодным для Этапа 5

Критерии приемки:
- новая игра стартует из валидного `QuestDefinition`
- runtime возвращает актуальные `GameState` и `PresentableState`
- корректный выбор переводит игру в следующий узел, некорректный отклоняется
- branch и end nodes обрабатываются корректно
- демонстрационный квест проходится end-to-end без save/load
- тесты покрывают happy path и ключевые failure-path сценарии runtime

В ответе после выполнения:
- перечисли реализованные классы и изменения в контрактах
- кратко опиши runtime flow новой игры, выбора и restore
- укажи, какие сценарии покрыты тестами
- отдельно отметь, что полноценные save/load и расширенная state-logic остаются на следующих этапах
```

## 4. Порядок Поставки

1. Контракты ядра

5. Save/load
6. CLI
7. Подготовка ко второму адаптеру

## 5. Критерии Приемки MVP

- Квест описан вне кодовой базы в JSON.
- Движок валидирует данные квеста до старта.
- Движок поддерживает ветвление и последствия.
- Сохранение и загрузка восстанавливают точный прогресс.
- CLI работает через общие application-контракты.
- Тесты покрывают core runtime и валидацию контента.

## 6. Стратегия Тестирования

Unit tests:

- вычисление условий
- применение эффектов
- правила переходов
- обработка невалидного выбора

Integration tests:

- загрузка квеста и старт сессии
- прохождение демонстрационной ветки A и ветки B
- сохранение по ходу игры и восстановление

Contract tests:

- фронтенд использует только application-level API

## 8. Рекомендуемый Первый End-to-End Срез

Первый сквозной срез должен быть намеренно маленьким:

- 4-6 узлов
- 1 флаг
- 1 числовая переменная
- 2 концовки
- 1 сценарий сохранения и загрузки

Этот срез подтверждает архитектуру до расширения схемы квестов.
