# Техническое Видение

## 1. Цель

Построить платформенно-нейтральный .NET-движок для текстовых квестов, в котором:

- контент квеста вынесен во внешние JSON-файлы
- runtime-логика общая для всех фронтендов
- UI-адаптеры не содержат логики ветвления и последствий
- сохранение и загрузка работают одинаково на разных платформах

Рекомендуемая базовая версия: `.NET 10`.

## 2. Архитектурный Стиль

Использовать компактную архитектуру Ports and Adapters.

Слои:

- `TextQuest.Domain`
- `TextQuest.Application`
- `TextQuest.Content.Json`
- `TextQuest.Infrastructure`
- `TextQuest.Frontends.Contracts`
- `TextQuest.Cli`
- `TextQuest.Telegram`
- `TextQuest.Desktop`
- `TextQuest.Mobile`
- `TextQuest.Tests`

## 3. Ответственность Слоев

`TextQuest.Domain`

- определения квестов
- модели узлов и выборов
- условия и эффекты
- игровое состояние
- доменные ошибки

`TextQuest.Application`

- запуск игры
- применение выбора
- построение текущего представления
- сохранение игры
- загрузка игры
- оркестрация runtime-потока

`TextQuest.Content.Json`

- десериализация JSON-файлов квестов
- валидация структуры квеста
- маппинг схемы файла в доменные объекты

`TextQuest.Infrastructure`

- файловое хранение сохранений
- сериализаторы
- платформенные сервисы, например время и логирование

`TextQuest.Frontends.Contracts`

- единая модель представления для любого фронтенда

Фронтенд-проекты

- рендерят текст и выборы
- получают ввод
- вызывают application-сервисы

## 4. Основные Доменные Понятия

`QuestDefinition`

- метаданные квеста
- идентификатор стартового узла
- начальные переменные
- коллекция узлов

`Node`

Типы узлов для MVP:

- `text`
- `decision`
- `branch`
- `end`

`Choice`

- id
- текст
- опциональные условия
- опциональные последствия
- id следующего узла

`GameState`

- id квеста
- версия квеста
- id текущего узла
- переменные
- флаги
- id посещенных узлов
- история решений
- статус завершения

`PresentableState`

- заголовок
- текстовые блоки
- видимые выборы
- флаг завершения
- метаданные результата

## 5. Runtime-Поток

Новая сессия:

1. Загрузить JSON квеста.
2. Провалидировать структуру.
3. Создать начальное игровое состояние.
4. Перейти в стартовый узел.
5. Разрешить автоматические ветки, пока не потребуется ввод игрока.
6. Вернуть `PresentableState`.

Ход игрока:

1. Фронтенд отправляет `choiceId`.
2. Движок проверяет, что выбор существует и сейчас доступен.
3. Движок применяет последствия.
4. Движок переходит в следующий узел.
5. Движок обрабатывает автоматические узлы.
6. Движок возвращает обновленный `PresentableState`.

Загрузка сессии:

1. Загрузить сохраненный `GameState`.
2. Загрузить соответствующее определение квеста.
3. Проверить `questId`, `questVersion` и `saveFormatVersion`.
4. Перестроить `PresentableState` по состоянию.

## 6. Система Сохранений

`GameState` должен храниться отдельно от контента квеста.

Файл сохранения должен включать:

- `saveId`
- `questId`
- `questVersion`
- `saveFormatVersion`
- `currentNodeId`
- `variables`
- `flags`
- `visitedNodes`
- `decisionHistory`
- `createdAt`
- `updatedAt`

Для MVP использовать JSON-файлы сохранений и файловое хранилище.

Правило совместимости для MVP:

- загружать только если `questId` и `questVersion` полностью совпадают

## 8. JSON-Формат Квеста

Структура верхнего уровня:

```json
{
  "questId": "sample_quest",
  "version": "1.0.0",
  "title": "Пример квеста",
  "startNodeId": "intro",
  "variables": {
    "trust": 0,
    "hasKey": false
  },
  "nodes": []
}
```

Рекомендуемая структура узла:

```json
{
  "id": "intro",
  "type": "text",
  "text": [
    "Вы просыпаетесь в запертой комнате.",
    "За дверью кто-то говорит."
  ],
  "choices": [
    {
      "id": "listen",
      "text": "Прислушаться",
      "consequences": [
        { "type": "add", "target": "trust", "value": 1 }
      ],
      "nextNodeId": "door_voice"
    },
    {
      "id": "break_door",
      "text": "Выломать дверь",
      "conditions": [
        { "var": "trust", "op": ">=", "value": 1 }
      ],
      "nextNodeId": "hallway"
    }
  ]
}
```

Рекомендуемый узел ветвления:

```json
{
  "id": "judge_outcome",
  "type": "branch",
  "branches": [
    {
      "condition": {
        "all": [
          { "var": "hasKey", "op": "==", "value": true }
        ]
      },
      "nextNodeId": "escape"
    }
  ],
  "defaultNextNodeId": "captured"
}
```

Рекомендуемый конечный узел:

```json
{
  "id": "escape",
  "type": "end",
  "text": ["Вы выбрались."],
  "result": "victory"
}
```

## 9. Правила Валидации Для MVP

- уникальные id узлов
- корректный `startNodeId`
- корректные ссылки в `nextNodeId`
- уникальные id выборов внутри узла
- только поддерживаемые типы узлов
- только поддерживаемые типы эффектов
- только поддерживаемые операторы условий
- отсутствие неразрешенных ссылок на переменные
- защита от бесконечных циклов в автоматических ветках

## 10. Стратегия По Фронтендам

Порядок поставки:

1. CLI
2. Telegram-бот
3. Desktop UI
4. Mobile app

Причина:

- CLI быстрее всего проверяет API движка
- Telegram хорошо проверяет stateless-взаимодействие и восстановление состояния
- Desktop и mobile должны использовать те же application-контракты после стабилизации ядра

## 11. Ключевые Риски И Снижение Рисков

- Риск: схема JSON слишком рано станет сложной.
  Снижение: держать схему MVP намеренно маленькой.

- Риск: фронтенд начнет дублировать логику движка.
  Снижение: наружу отдавать только `PresentableState` и runtime-команды.

- Риск: сохранения станут несовместимыми после изменения квеста.
  Снижение: строгая проверка версии в MVP.

- Риск: бесконечные циклы в автоматических ветках.
  Снижение: валидатор плюс ограничение числа runtime-шагов.

- Риск: переусложнение сразу под все платформы.
  Снижение: сначала движок и CLI, потом остальные адаптеры.
