# Документ Геймдизайна

## 1. Цель Продукта

Создать универсальный движок текстовых квестов на .NET, в котором один и тот же контент квеста может запускаться через разные каналы доставки:

- CLI-приложение
- desktop UI-приложение
- мобильное приложение
- Telegram-бот

Движок должен отделять контент квеста от runtime-логики и от логики интерфейса.

## 2. Принципы Продукта

- Платформа строится вокруг движка, а не вокруг конкретного сюжета
- Один runtime, много фронтендов
- Логика квеста описывается данными, а не зашитыми UI-сценариями
- При одинаковом состоянии и одинаковых выборах поведение должно быть детерминированным
- Поддержка сохранения и загрузки является базовой функцией, а не дополнением
- Ветвление и последствия должны расширяться без переписывания ядра

## 3. Возможности Для Игрока

- Читать повествование сцена за сценой
- Делать выбор из доступных вариантов
- Видеть разные ветки в зависимости от предыдущих решений
- Проходить ветвящиеся диалоги и получать разные исходы
- Продолжать игру с того же места и с тем же состоянием после повторного запуска
- Переигрывать квест и получать другие результаты

## 4. Возможности Для Автора

- Описывать квесты декларативно в JSON
- Задавать сцены, узлы диалога, выборы, переходы, условия и эффекты
- Отслеживать переменные, флаги, посещенные узлы и историю решений
- Скрывать или открывать выборы на основе прошлого состояния
- Использовать один и тот же квест в разных фронтендах
- Проверять контент до запуска

## 5. Нарративная Модель

Движок должен рассматривать квест как граф узлов.

Каждый узел может содержать:

- отображаемый текст
- опциональные данные о говорящем или метаданные диалога
- условия входа
- эффекты при входе
- ноль или более выборов
- правила перехода

Поддерживаемые типы потока:

- линейное прохождение
- явное ветвление
- автоматическое ветвление по условиям
- ветвящийся диалог
- повторные посещения узлов
- несколько финалов

## 6. Модель Последствий

Каждое значимое решение игрока должно отражаться в игровом состоянии.

Модель состояния должна поддерживать:

- булевы флаги
- числовые переменные
- строковые значения или теги
- историю посещения узлов
- историю ключевых решений
- в будущих итерациях опционально коллекции наподобие инвентаря

Последствия выбора могут:

- устанавливать флаг
- изменять переменную
- открывать или блокировать будущие выборы
- менять направление дальнейших веток
- влиять на доступность концовок
- изменять путь диалога

## 7. Требования К Сохранению И Загрузке

Поддержка сохранения и загрузки обязательна.

Движок должен сохранять как минимум:

- идентификатор квеста
- версию квеста
- идентификатор текущего узла
- все значимые переменные и флаги
- историю выборов, необходимую для будущих веток
- версию формата сохранения

Ожидаемое поведение:

- ручное сохранение
- позже возможность автосохранения или контрольных точек
- полное восстановление прогресса и последствий
- явная обработка несовместимых сохранений

## 8. Требования К Портируемости

Ядро движка не должно зависеть от конкретного UI.

Задачи фронтенда:

- отображать текущий текст и выборы
- отправлять ввод игрока в движок
- показывать завершение, ошибки, сохранение и загрузку

Задачи движка:

- вычислять условия
- применять последствия
- разрешать переходы
- формировать текущее представление состояния
- сохранять и восстанавливать игровое состояние

## 9. Нецели Для MVP

- без редактора квестов
- без встроенного визуального scripting UI
- без боевой подсистемы
- без механик реального времени
- без системы генерации сюжета
- без привязки к конкретному жанру или сеттингу

## 10. Функциональные Требования

Платформа должна:

- загружать определения квестов из JSON
- валидировать структуру квеста до запуска
- начинать новую сессию со стартового узла
- показывать текущий текст и доступные выборы
- вычислять доступность выбора на основе состояния
- применять эффекты атомарно
- детерминированно переходить к следующему узлу
- поддерживать ветвящиеся диалоги и ветвящиеся сцены в одной базовой модели
- сохранять и загружать полный прогресс
- предоставлять frontend-нейтральный runtime API

## 11. Критерии Успеха

- Один и тот же квест запускается в нескольких клиентах без переписывания игровой логики.
- Решения игрока надежно влияют на последующие ветки.
- Сохранение и загрузка полностью восстанавливают прогресс.
- Новые фронтенды можно добавлять без изменения базовой нарративной модели.
- Новый контент можно создавать без модификации кода движка для типовых ветвящихся сценариев.
